Blueprint Técnico: Assistente de Crafting Inteligente para Path of Exile 2Preâmbulo: Sumário Executivo e Desafios CentraisVisão do ProjetoO objetivo deste documento é fornecer um blueprint técnico completo para o desenvolvimento de um assistente de crafting inteligente para o jogo Path of Exile 2 (PoE2). A funcionalidade central desta ferramenta será analisar o mercado de trocas em tempo real para identificar os itens base mais economicamente viáveis para um objetivo de crafting específico definido pelo usuário. A "inteligência artificial" (IA) do sistema não será um modelo de aprendizado de máquina, mas sim um algoritmo de otimização projetado para simular resultados de crafting, calcular custos esperados e, por fim, minimizar o investimento de currency do jogador.Estratégia Técnica CentralA arquitetura do projeto se apoiará em dois pilares fundamentais: (1) a interação com a API de trocas não oficial da Grinding Gear Games (GGG) para obter dados de mercado ao vivo, e (2) uma base de conhecimento local abrangente sobre as mecânicas do jogo, derivada de recursos data-mined mantidos pela comunidade. Esta abordagem de sistema duplo permite que a aplicação combine a volatilidade do mercado com as regras estáticas do jogo para fornecer recomendações acionáveis e baseadas em dados.Desafios Críticos e PremissasA execução deste projeto enfrenta obstáculos técnicos significativos que devem ser compreendidos desde o início para garantir uma arquitetura resiliente e expectativas realistas.A API Não Documentada: A documentação oficial para desenvolvedores fornecida pela GGG 1 descreve um sistema baseado em OAuth 2.1 para gerenciamento de contas e acesso a dados privados. Contudo, este não é o sistema utilizado pelo site público de trocas. A funcionalidade de busca de itens, que é o coração deste projeto, opera através de uma API interna, não documentada, e que está sujeita a alterações sem aviso prévio.3 Ferramentas estabelecidas, como o Path of Building, confirmam o uso desta API interna, que depende de requisições diretas aos endpoints /api/trade/....5 A viabilidade de todo o projeto depende da estabilidade e acessibilidade contínua desta API interna. A arquitetura deve ser projetada com modularidade para mitigar o risco de mudanças abruptas.A "Caixa Preta" dos Pesos de Modificadores em PoE2: Este representa o maior risco para a precisão do sistema. Análises de dados do jogo para PoE2 indicam que os "pesos" (weights) dos modificadores — que determinam a probabilidade de um afixo específico ser gerado durante o crafting — foram removidos dos arquivos do cliente e são, presumivelmente, gerenciados inteiramente do lado do servidor.6 Em PoE1, esses pesos eram a base para todos os cálculos de probabilidade em ferramentas como o Craft of Exile. A ausência desses dados significa que qualquer cálculo de probabilidade de crafting será, na melhor das hipóteses, uma estimativa informada. O algoritmo de otimização deve ser projetado para operar com essa incerteza inerente, possivelmente utilizando modelos de probabilidade uniformes como ponto de partida, com a capacidade de incorporar dados empíricos no futuro.Um Alvo em Movimento: Path of Exile 2 ainda está em fase de desenvolvimento. Mecânicas de jogo, dados de itens, afixos e a própria estrutura da API de trocas podem e irão mudar. A arquitetura do software deve ser altamente modular, permitindo que componentes como o cliente da API, o serviço de dados do jogo e o motor de simulação de crafting sejam atualizados de forma independente para se adaptarem a novas versões do jogo com o mínimo de reengenharia.Parte 1: Coleta de Inteligência Fundamental: Fontes de Dados e IntegraçãoEsta seção detalha a aquisição, estruturação e integração dos dois fluxos de dados críticos para a operação da ferramenta: dados de mercado em tempo real e dados estáticos de mecânicas de jogo.1.1. Interface com a API de Trade da GGG: Um Guia de Engenharia ReversaA interação bem-sucedida com o mercado de PoE2 exige uma compreensão precisa de como o site oficial de trocas funciona internamente. A análise de ferramentas existentes e discussões na comunidade de desenvolvedores revela que o site público não utiliza a API OAuth documentada, mas sim um conjunto de endpoints internos que devem ser replicados.3O Processo de Busca Assíncrona em Duas EtapasPara otimizar o desempenho e gerenciar o cache de resultados, a API de trocas emprega um mecanismo de busca em duas etapas. Uma aplicação cliente deve respeitar este fluxo para funcionar corretamente.Etapa 1: POST /api/trade/search/{league}: O cliente envia um payload JSON complexo que define todos os critérios de busca para este endpoint. O servidor processa a requisição, gera um resultado de busca em cache e retorna uma resposta contendo um ID de consulta (id) e uma lista dos primeiros hashes de itens correspondentes (result).3 Este método não retorna os dados completos dos itens, apenas seus identificadores únicos.Etapa 2: GET /api/trade/fetch/{item_hashes}: O cliente então utiliza os hashes de itens retornados na primeira etapa para construir uma URL para este segundo endpoint. Os hashes são concatenados em uma string separada por vírgulas. Esta requisição GET retorna o conjunto completo de dados para os itens especificados. O ID de consulta da Etapa 1 pode ser usado para buscar "páginas" subsequentes de hashes de resultados, permitindo a paginação.Este design implica que o módulo cliente da API da aplicação (TradeAPIClient) deve ser stateful, gerenciando o ID da consulta e os hashes de itens para buscar resultados em lotes. Esta abordagem evita timeouts, respeita o design da API e permite o manuseio eficiente de buscas que retornam um grande número de itens.A tabela a seguir resume os endpoints essenciais para a interação com o sistema de trocas.EndpointMétodoDescrição/api/trade/search/{league}POSTSubmete uma consulta de busca e retorna um ID de consulta e um lote inicial de hashes de itens./api/trade/fetch/{hashes}GETBusca os dados detalhados para uma lista de hashes de itens separados por vírgula./api/trade/data/leaguesGETRecupera uma lista de todas as ligas disponíveis, essencial para construir a URL de busca./api/trade/data/statsGETRecupera uma lista abrangente de todos os stats pesquisáveis e seus IDs internos. Crucial para a construção do payload de busca./api/trade/data/itemsGETRecupera uma lista de todos os itens do jogo, incluindo tipos de base e itens únicos.Anatomia de uma Consulta de Busca (Payload POST)A construção correta do payload JSON para o endpoint de busca é a parte mais crítica da integração com a API. O objeto raiz contém duas chaves principais: query e sort.query: Este objeto contém todos os filtros de busca.status: Filtra por status do jogador (ex: {"option": "online"}) para garantir que apenas vendedores ativos sejam retornados.7stats: Uma lista de objetos, onde cada objeto representa um grupo de filtros de modificadores. Este é o componente mais complexo, permitindo lógicas and, not, count, e if.filters: Um objeto que contém filtros não relacionados a modificadores, como categoria do item, tipo de base, número de engastes (sockets), influências, nível do item, etc.sort: Define o critério de ordenação dos resultados, geralmente por preço ({"price": "asc"}).A estrutura para filtrar por modificadores dentro de stats é particularmente detalhada. Cada filtro é um objeto com um id, um objeto value e um booleano disabled.id: O identificador interno da GGG para o stat (ex: explicit.stat_3299347043 para "+# to maximum Life"). Estes IDs são obtidos do endpoint /api/trade/data/stats.value: Um objeto contendo min e/ou max para especificar um intervalo numérico para o valor do modificador.disabled: Um booleano que, quando true, inverte a lógica do filtro, buscando itens que não possuem o modificador especificado.A tabela abaixo fornece um exemplo anotado de um payload JSON para uma busca complexa, demonstrando a estrutura aninhada.ChaveTipoExemploDescriçãoqueryObjeto{...}O contêiner principal para todos os filtros de busca.query.statusObjeto{"option": "online"}Filtra por jogadores que estão online no jogo.query.filtersObjeto{...}Contêiner para filtros de propriedades do item.query.filters.type_filtersObjeto{"filters": {"category": {"option": "armour.chest"}}}Filtra pela categoria do item, neste caso, peitorais.query.filters.misc_filtersObjeto{"filters": {"ilvl": {"min": 86}}}Filtra por propriedades diversas, como nível do item (item level).query.statsLista[{"type": "and", "filters": [...]}]Lista de grupos de filtros de modificadores. type: "and" significa que todos os filtros dentro do grupo devem ser satisfeitos.query.stats.filtersObjeto{"id": "explicit.stat_123...", "value": {"min": 90}}Filtra por um modificador explícito específico (ex: vida) com um valor mínimo.query.stats.filtersObjeto{"id": "explicit.stat_456...", "disabled": true}Filtra para excluir itens que possuem um modificador específico (ex: mana).sortObjeto{"price": "asc"}Define a ordenação dos resultados, neste caso, por preço ascendente.Melhores Práticas da APIPara garantir uma operação estável e evitar bloqueios, a aplicação deve seguir certas práticas recomendadas.User-Agent: Todas as requisições devem incluir um cabeçalho User-Agent descritivo. Embora a API seja não oficial, esta é uma prática padrão de boa cidadania na web que ajuda os administradores da GGG a identificar o tráfego. Exemplo: User-Agent: NomeDaSuaApp/1.0 (contato: seu@email.com) - Projeto não comercial.Rate Limiting: A API impõe limites de requisição. A aplicação deve ser capaz de lidar com respostas de status 429 Too Many Requests. A implementação de uma estratégia de recuo exponencial (exponential backoff) é mandatória. Além disso, o design da aplicação deve minimizar o número de requisições, por exemplo, agrupando o maior número possível de hashes de itens em uma única chamada ao endpoint /api/trade/fetch/.POESESSID: Para certas funcionalidades, como visualizar inventários privados, a API pode exigir um cookie POESESSID válido.5 Embora não seja estritamente necessário para buscas públicas, que são o foco deste projeto, o TradeAPIClient deve ser projetado para incluir opcionalmente este cookie, aumentando sua flexibilidade.1.2. Construindo a Base de Conhecimento de Crafting: Utilizando o RePoEA fonte de dados estáticos mais robusta e confiável para as mecânicas de Path of Exile não é um site de terceiros como o Craft of Exile, mas sim o projeto que fornece os dados para ele: o RePoE.9 O RePoE é um repositório mantido pela comunidade que extrai e processa os arquivos de dados brutos do jogo (.ggpk) em arquivos JSON estruturados e legíveis por máquina.10 Ao utilizar o RePoE diretamente, a ferramenta se torna independente de qualquer interface de usuário de terceiros e constrói sua lógica a partir da fonte de dados mais próxima da verdade do jogo, uma prática adotada por outras ferramentas importantes da comunidade, como o Path of Building.Aquisição dos DadosOs dados serão adquiridos através do clone de um fork do repositório RePoE que está sendo ativamente mantido com os dados de PoE2. Um candidato provável é o repoe-fork.github.io/poe2/, mencionado em discussões de desenvolvedores.6 A aplicação deve incluir um mecanismo para atualizar periodicamente sua cópia local destes dados, puxando as últimas alterações do repositório para se manter sincronizada com as atualizações do jogo.Arquivos de Dados Essenciais e Suas Inter-relaçõesA capacidade da aplicação de traduzir os objetivos de um usuário em consultas de API e simulações de crafting depende da correlação inteligente de informações de vários arquivos JSON do RePoE. A API de trocas opera com IDs internos, enquanto os usuários pensam em termos de nomes de stats. Os arquivos do RePoE servem como a "Pedra de Roseta" para essa tradução.Por exemplo, para buscar um item com "+# de Vida máxima", a aplicação deve executar um processo de mapeamento em várias etapas:Consultar o arquivo stat_translations.json para encontrar o texto legível por humanos ("+# to maximum Life") e obter a lista de IDs de stats associados.Utilizar esses IDs de stats para encontrar as entradas de modificadores correspondentes em mods.json (ex: o modificador "Healthy").Construir o ID completo do stat para a API (ex: explicit.stat_...), que é obtido do endpoint /api/trade/data/stats e deve estar alinhado com os dados do RePoE.Usar este ID completo para construir o payload JSON da busca.Este processo de mapeamento não é uma simples busca chave-valor e requer um serviço dedicado dentro da arquitetura da aplicação (CraftingDataService) para gerenciar essas complexas relações de dados. Embora factualmente incorreta, esta premissa estabelece uma linha de base funcional para o algoritmo de cálculo de custos.Estratégia Avançada (Adaptativa): Uma solução mais robusta é projetar a aplicação para carregar um arquivo de pesos separado e mantido pela comunidade. A arquitetura pode ser configurada para buscar este arquivo de um repositório GitHub dedicado, permitindo que a comunidade colabore na coleta de dados empíricos (através do registro de milhares de crafts) para refinar as probabilidades. Isso torna a ferramenta adaptável e progressivamente mais precisa ao longo do tempo, sem exigir mudanças no código principal.Parte 2: Arquitetura do Sistema e Lógica CentralEsta parte delineia a estrutura do software e o algoritmo que constitui sua "inteligência" de otimização.2.1. Um Blueprint Arquitetural ModularUma arquitetura modular é essencial para a manutenibilidade e escalabilidade do projeto, especialmente considerando a natureza instável do ecossistema de PoE2. A aplicação será dividida em três componentes lógicos principais, cada um com uma responsabilidade clara.TradeAPIClient (A Camada de Rede): Este módulo será exclusivamente responsável por toda a comunicação com a API de trocas da GGG. Ele encapsulará a complexidade da formação de requisições, envio, tratamento de respostas, gerenciamento de limites de taxa e tratamento de erros. Ele exporá métodos simples e de alto nível para o resto da aplicação, como searchForItems(query) e fetchItemDetails(hashes).CraftingDataService (A Camada de Conhecimento): Este serviço atuará como a única fonte da verdade para todos os dados estáticos do jogo. Na inicialização, ele carregará todos os arquivos JSON necessários do RePoE em memória, em estruturas de dados otimizadas para consulta rápida. Ele fornecerá métodos para consultar esses dados, como getStatIdForText(text), getModsForItem(itemBase) e, crucialmente, getProbabilitiesForCraft(item, currencyAction). A lógica para lidar com o "problema dos pesos" residirá aqui.CraftingSolverEngine (A Camada Lógica): Este é o cérebro da aplicação. O motor de resolução orquestrará os outros dois serviços para atingir o objetivo do usuário. Ele receberá o alvo de crafting, usará o CraftingDataService para entender as possibilidades e probabilidades, usará o TradeAPIClient para encontrar itens candidatos no mercado e, finalmente, executará o algoritmo de análise de custo em cada candidato para encontrar a solução ótima.2.2. Esta definição será encapsulada em uma estrutura de dados (objeto/classe) chamada CraftingTarget.Exemplo de Estrutura:JSON{

2.3. O Motor de Resolução de Crafting: O Algoritmo de Análise de CustoEste é o processo passo a passo que o CraftingSolverEngine seguirá para cada requisição do usuário. O objetivo é transformar um desejo de item em uma lista classificada de pontos de partida mais baratos.Formulação da Consulta: O motor recebe o CraftingTarget. Ele usa o CraftingDataService para traduzir os afixos desejados em um ou mais payloads de consulta para o TradeAPIClient. A inteligência aqui reside na geração de múltiplas consultas estratégicas. Por exemplo, o motor não buscará apenas por bases limpas, mas também por bases que já possuam um ou dois dos modificadores desejados, especialmente os mais raros. Isso amplia o espaço de busca para incluir itens parcialmente completos que podem ser significativamente mais baratos de finalizar.Aquisição de Candidatos: O TradeAPIClient executa as consultas geradas e retorna uma lista de itens candidatos disponíveis no mercado, incluindo seus dados completos e preço de compra.Simulação de Crafting e Estimativa de Custo: Para cada item candidato, o motor executa uma simulação para estimar o custo de transformá-lo no CraftingTarget.Ele primeiro calcula a "distância" entre o estado atual do item candidato e o estado final desejado (quantos afixos corretos faltam, quantos afixos errados precisam ser removidos, se possível).Em seguida, ele simula a sequência de passos de crafting mais provável para fechar essa lacuna, com base nas mecânicas de PoE2.11 Por exemplo:Se falta um prefixo e há um espaço aberto, qual é o custo de usar um Exalted Orb? O custo é calculado como (Preço de 1 Exalted Orb) / (Probabilidade de acertar um dos afixos desejados).Se um item precisa ser atualizado de Mágico para Raro, o motor simula o uso de um Regal Orb ou de uma Essência relevante, comparando os custos e probabilidades de cada rota.12A simulação deve levar em conta a ausência confirmada de Orbs of Scouring em PoE2, o que torna a remoção de modificadores um processo muito mais restrito e arriscado, aumentando o custo de "consertar" um erro de crafting.13O CraftingDataService é consultado a cada passo para fornecer as probabilidades necessárias para esses cálculos (utilizando a estratégia de pesos definida).Pontuação e Classificação dos Itens Base: O motor calcula uma pontuação final para cada item candidato, que representa o custo total estimado para se chegar ao item final.A fórmula é: CustoTotalEstimado=PrecoDeCompra+∑(CustoEstimadoDeCadaPassoDeCrafting)Os itens candidatos são então classificados por este custo total, do menor para o maior.Apresentação dos Resultados: A lista classificada é apresentada ao usuário, fornecendo informações claras e acionáveis para cada opção. Isso inclui o item base, seu preço, o custo estimado de crafting, o custo total e um resumo dos passos de crafting sugeridos.Parte 3: Roteiro de Implementação para "Jules"Esta seção fornece um guia sequencial e direto para o desenvolvimento da aplicação, destinado a ser executado por uma IA de desenvolvimento.Passo 1: Estabelecer a Fundação de Dados (CraftingDataService)Aquisição de Dados: Desenvolver um script para clonar ou baixar a versão mais recente dos dados do RePoE compatíveis com PoE2. Este script deve ser executável periodicamente para manter os dados atualizados.Modelagem de Dados: Criar modelos de dados (classes ou structs na linguagem de programação escolhida) para representar as entidades principais: BaseItem, Mod, Stat, Essence, etc.Implementação do Serviço: Implementar o CraftingDataService para carregar os arquivos JSON (base_items.json, mods.json, etc.) nos modelos de dados na inicialização da aplicação.Implementação das Consultas: Implementar os métodos centrais de consulta de dados: getModById(id), getBaseItemByName(name), getModsByTag(tag), e a função crucial de mapeamento translateTextToStatIds(text).Lógica de Probabilidade: Implementar a lógica para cálculo de probabilidades de afixos. Começar com a premissa de "pesos iguais", mas arquitetar o sistema de forma que este módulo de probabilidade possa ser facilmente substituído por um mais avançado (que leia um arquivo de pesos customizado) no futuro.Passo 2: Construir a Camada de Rede (TradeAPIClient)Cliente HTTP: Implementar um cliente HTTP capaz de realizar requisições GET e POST. Garantir que ele configure corretamente o cabeçalho User-Agent em todas as chamadas.Método de Busca (searchForItems):Implementar a serialização de um objeto de consulta para uma string JSON.Realizar a requisição POST para /api/trade/search/{league}.Desserializar a resposta para extrair o ID da consulta e a lista de hashes de itens.Método de Detalhes (fetchItemDetails):Implementar a função que recebe uma lista de hashes, os une em uma string separada por vírgulas e realiza a requisição GET para /api/trade/fetch/{hashes}.Tratamento de Erros: Implementar um tratamento de erros robusto, com atenção especial ao código de status 429 Too Many Requests, que deve acionar uma lógica de recuo exponencial.Exemplo de Payload: Fornecer no código-fonte um exemplo completo e anotado de um payload de busca complexo como referência. Isso deve incluir menus suspensos para tipos de base e listas pesquisáveis para modificadores, com autocompletar, de forma semelhante à interface do Craft of Exile.15Feedback de Processamento: Enquanto o CraftingSolverEngine estiver executando seus cálculos (o que pode levar vários segundos devido às chamadas de rede e simulações), a UI deve exibir um indicador claro de carregamento ou progresso.Saída de Resultados: A página de resultados deve exibir uma lista classificada dos N melhores itens base (ex: top 10). Cada entrada na lista deve mostrar claramente:A renderização visual do item.O nome do vendedor e o preço de compra.Uma decomposição do Custo Total Estimado (Preço de Compra + Custo Estimado de Crafting).Um botão para copiar a mensagem de sussurro (whisper) no jogo para contatar o vendedor.Uma visualização expansível que detalha os passos de crafting recomendados pelo motor.Conclusão e Trabalhos FuturosSumário do EntregávelEste documento fornece um blueprint arquitetural e algorítmico completo para o Assistente de Crafting Inteligente de PoE2. Seguindo este roteiro, um sistema de desenvolvimento como "Jules" pode construir sistematicamente uma ferramenta poderosa que resolve um problema complexo de otimização para os jogadores, traduzindo objetivos de crafting em estratégias de aquisição de itens eficientes e econômicas.Recapitulação dos Riscos ChaveÉ imperativo reiterar os riscos primários que fundamentam a arquitetura desta aplicação: a dependência de uma API não documentada e a incerteza fundamental em torno das probabilidades de crafting em PoE2 devido aos pesos de modificadores do lado do servidor. A modularidade e a capacidade de adaptação da aplicação são as principais estratégias de mitigação para esses riscos.Melhorias FuturasApós a implementação da funcionalidade central, a ferramenta pode ser expandida com vários recursos avançados:Métodos de Crafting Avançados: Incorporar mecânicas de crafting mais complexas à medida que forem reveladas e compreendidas para PoE2, como o crafting de Desecration 12 ou o uso de Recombinators.13Rastreamento Histórico de Preços: Integrar-se com um serviço de economia de mercado (como o poe.ninja para PoE1, caso surja um equivalente para PoE2) para levar em conta a volatilidade dos preços das currencies, resultando em cálculos de custo ainda mais precisos.9Aprendizado de Máquina para Pesos: Se for possível coletar um volume suficiente de dados (por exemplo, através do registro anônimo de crafts realizados pelos usuários da ferramenta), um modelo de aprendizado de máquina simples poderia ser treinado para prever os pesos dos modificadores com maior precisão do que a premissa de linha de base, transformando a ferramenta em um sistema verdadeiramente adaptativo e orientado por dados.
